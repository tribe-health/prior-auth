# PatientGPT storage, identity, and deployment team research

Observed 2026-10-04. Phase: spec / bootstrap ready. Scope: team design and dependency research only; no application, dependency, cluster, or workflow changes. Confidence below describes inspected source, not runtime acceptance.

The useful reuse boundary is the shell-independent `aso_host::AppServices` and its domain ports. Forge's database abstraction, Fabric's replication stores, and the browser entity graph serve different responsibilities. They are not interchangeable clinical databases. The uncomfortable thing is that the requested desktop SurrealDB 3.3.0 direction differs from the inherited desktop SQLite preference, while the inherited browser materializer is explicitly blocked. Assign an owner to reconcile and prove each boundary before declaring storage integration ready.

## Identity and edge integration

Kratos supplies identity/session validation. Flint Gate supplies request authentication, authorization, claims enrichment, and stream enforcement, analogous to the identity access proxy role of Oathkeeper. Envoy Gateway supplies ingress routing and can delegate authorization to a separate service. These are distinct ownership seams.

- `/Users/gqadonis/Projects/prometheus/flint-gate/crates/flint-gate-core/src/auth/kratos.rs:97-147,194-200` accepts one Authorization or configured session-cookie credential and rejects competing credentials. It does not select `x-session-token` in that function.
- `/Users/gqadonis/Projects/TribeHealth/kevin/prior-auth/crates/aso-web-server/src/adapters/session.rs:69-121` forwards cookies or native `x-session-token` to whoami, handles 401/403/unavailability distinctly, and creates a user principal. Delegated agents need a separate provider. This is an actual adapter mismatch to settle at the shared auth contract, not a reason to equate a clinician with an agent.
- `/Users/gqadonis/Projects/TribeHealth/kevin/prior-auth/crates/aso-web-server/src/adapters/kratos_proxy.rs:28-35,55-88` proxies browser login/recovery and preserves cookie/redirect headers. A deployed native login/logout and secure credential lifecycle was not exercised here.
- Official [Kratos sessions](https://github.com/ory/docs/blob/master/docs/kratos/session-management/01_overview.mdx) documents cookie/native session validation. Official [Oathkeeper integration](https://github.com/ory/docs/blob/master/docs/kratos/guides/zero-trust-iap-proxy-identity-access-proxy.mdx) uses the cookie-session authenticator against whoami. These do not make every native header accepted by every local adapter.
- Official [Envoy Gateway external authorization](https://gateway.envoyproxy.io/docs/tasks/security/ext-auth) configures `SecurityPolicy.extAuth.http` and allowed identity headers to the backend. [API reference](https://gateway.envoyproxy.io/docs/api/extension_types) says HTTP authorization forwards a limited default header set; cookie forwarding therefore needs deliberate configuration. Fail-open behavior and actual installed CRD semantics must be checked before implementation.
- The inspected Flint Gate checkout (`39c40d6`) identifies itself as an Oathkeeper replacement in `README.md:7`, but searching its Rust source for `ext_authz`, `ext-authz`, and Envoy produced no implementation match. Do not assert this checkout exposes a working Envoy check endpoint. It may differ from the deployed digest or another branch.

Read-only cluster observation used explicit `--context know-me` on every call, no Secret reads and no raw kubeconfig. `kubectl --context know-me get deployments -n envoy-gateway-system -o custom-columns=NAME:.metadata.name,READY:.status.readyReplicas,IMAGES:.spec.template.spec.containers[*].image --request-timeout=15s` returned one ready controller at Envoy Gateway v1.9.1 and ready Envoy v1.39.1 data planes. `get httproutes -n flint-core` returned routes for `gate.know-me.tools`, `api.know-me.tools`, `rt.know-me.tools`, `auth.know-me.tools`, and `sso.know-me.tools`, all parented by `argocd-gateway`. Flint Gate and Forge each had two ready replicas, Fabric one, Kratos one at `oryd/kratos:v26.2.0`.

The only listed SecurityPolicy was `ipfs/ipfs-webui-auth`; a selected-field inspection showed `specKeys: [basicAuth, targetRefs]`, `extAuth: null`, and Accepted=True. This does **not** prove ext_authz protects the Flint routes. The observations prove resource presence/readiness only, not session correctness, tenant enforcement, PHI placement, deployment source ownership, or PatientGPT deployment readiness.
