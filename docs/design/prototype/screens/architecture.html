Seven components.
Stated as they are, not as we'd like them.

This product runs on an open runtime stack built for governed AI agents. Below is what each part does, what it actually ships today, and what it does not. Where a capability is planned rather than built, this page says so — an architecture document that presents a roadmap as shipped is worse than one that admits the boundary.

01 · The shape

One database of record, one governed agent runtime, one realtime spine, and three surfaces that share an architecture rather than a codebase. The layers below read from the user inward.

Surfaces React 19 web · Tauri 2 desktop · Flutter mobile. Same design tokens, same entity contracts, same event vocabulary — three implementations, one architecture.
Entity layer Prometheus Entity Management — a normalized reactive entity graph with a local store per tier, so the interface reads one canonical copy of every record.
Gateway Flint Gate — auth proxy and policy boundary. Verifies the session, decides the action, streams the run. Never an identity provider itself.
Agent runtime Universal Agent Runtime — executes agents, routes models, governs every tool call, and emits a normalized event stream.
Realtime Flint Realtime Fabric — a durable event spine with per-event authorization, so a determination arriving pushes to every open client instead of being polled for.
Automation LibreFang — scheduled and durable agent work: watching payer policies, chasing disputed items, resuming a case when a payer finally answers.
Data plane PostgreSQL 18 with pgvector, fronted by Flint Forge. Sixty tables, and the clinical safety rules enforced as triggers rather than conventions.
02 · Agent runtime
universal-agent-runtimev1.0.0 · Rust · MIT

A single Rust process that executes agents, routes models, manages knowledge and memory, governs tools, and streams structured events — behind one HTTP/SSE boundary. The interface never talks to a model provider, a tool, or storage directly; every capability crosses a policy-enforced boundary.

Agents are Markdown, compiled and signed. An agent is a document with fifteen required sections — identity, capabilities, tools, knowledge, memory, governance, budgets — compiled through eight stages into a signed descriptor. Governance is enforced at compile time: the definition must embed policy text, and compilation fails if any sensitive capability lacks explicit coverage or explicit denial. A declared capability never implies permission.

Model routingCapability filter, then provider health, then preference — a model in cooldown cannot win because policy picked it earlier
CertifiedOpenAI-compatible and Anthropic paths, plus local embeddings
Local laneEmbeddings only — local chat generation is not first-party
Egress lockA single driver constructor can refuse every non-loopback address and fail closed
MobileLibrary embedding, not a sidecar — and it currently boots with an empty skill registry
Generated interfacesA2UI · certified catalog

When an assistant needs to ask something — a clarifying question, an approval, a structured form — it emits a typed projection rather than markup. Unknown component types fail closed, and model-provided HTML and JavaScript are never executed.

The rule that governs it is one sentence: a projection describes what the runtime decided; it does not grant authority. Actions route back through the runtime carrying run, event, and idempotency identifiers, so a duplicate submission is absorbed rather than acted on twice.

CatalogNine certified protocol components plus seven entity extensions
RenderersReact, Lit, and Svelte over one shared state model

RuleCompletion is never inferred from prose — only from an explicit terminal event
03 · Data and API
flint-forgev1.0.0 · Rust · PG 18

Turns a PostgreSQL database into a self-describing API surface. It is three things at once: a suite of in-database extensions, a gateway service, and a compiler. The source of truth is the live database catalog — schema changes fire event triggers that recompile the API in place, with no process restart.

One pattern here matters more than the rest for a clinical feed. Write-ahead replication bypasses row-level security, so for every change event the gateway re-queries the changed row as the subscriber, with full security context, before delivering it. Streaming does not become a way around the permissions the database enforces.

GeneratesREST, GraphQL, and one typed agent tool per table
Vectorpgvector with automatic HNSW indexes and hybrid keyword-plus-vector search
PolicyCedar policies stored in-database, fail-closed by construction
TenancyRow-level security is the authoritative gate; forced, not merely enabled
In-database embeddingCorrection · read this

The stack offers a SQL function that embeds text — llm.embed() — and a declarative form that adds a vector column, builds the index, installs a trigger, and backfills. It is genuinely useful, and it is the model our own schema follows.

But it does not keep data inside the database. The extension is an HTTP client: it builds a request and sends the text to the gateway, and onward to a model provider. A summary of this architecture elsewhere describes retrieval as running "beside the data — criteria never leave the box." For the published policy corpus that is a fair description of intent. For patient text it is not what the code does, and calling a SQL function does not change where the bytes go.

We state it plainly because it is the kind of assumption that produces a breach: the call looks in-database.

04 · Identity and authorization
flint-gate + Ory KratosRust · OAuth 2.1 resource server

An auth proxy purpose-built for streaming AI workloads. It verifies sessions, decides actions against a policy engine, and streams the result without buffering. Its stated posture is worth repeating: it federates any standards-capable identity provider and never becomes one.

The mechanism that solves our hardest problem. An AI assistant must be able to act for a surgeon without inheriting the surgeon's clinical authority. Delegation produces a token carrying an actor claim, and that claim classifies the caller as a different entity type — an agent, not a user.

Our database adds a third layer beneath this one. The gateway decides whether a caller may invoke a tool; the database decides whether the resulting act is clinically permitted. Neither substitutes for the other — and because a service role can bypass row-level security, the trigger-enforced clinical rules are a genuine complement rather than a duplicate.

05 · Entities and client state
prometheus-entity-managementv3.2 web · v3.1 Flutter

A normalized reactive entity graph. Lists hold only ordered identifiers; every view rejoins the same record at render time. One write updates the list row, the detail panel, and the badge together, because they were never separate copies.

The layering argument is deliberate: a query cache models requests — is this response stale? A local-first app models data, and the sync engine already owns staleness. A cache on top re-answers that in the wrong layer with a second source of truth that drifts. The project enforces this — an audit script fails a build that reintroduces one.

Web storePGlite — PostgreSQL compiled to WebAssembly, in the browser
DesktopThe same engine natively, through typed commands
MobileSQLite through a Rust bridge
ConflictsLast-write-wins by default, swappable to CRDT merge per entity type
OfflineA durable queue with exponential backoff; exhausted actions are set aside rather than blocking the queue
Typed payloadsRuntime schema registry

The same metadata-driven pattern our database uses appears again in the client. A schema can be registered per entity type and per field, so a request whose payload varies by type resolves its shape at render time rather than needing a separate component per variant.

An honest limit: the graph is untyped at runtime and the registry is a lookup, not a validator. Nothing in it binds a record's type to its payload schema. That enforcement is ours to write — which is exactly what the database triggers do on the server side.

06 · Realtime
flint-realtime-fabricRust · 27 crates

A durable event spine. A determination arriving from a payer pushes to every open client — the scheduler sees it without polling, and the coordinator does not refresh a queue to find out.

Subscriptions are permission-filtered twice. A channel gate checks whether the subscriber may listen at all, and then every individual event is re-checked against the subscriber's permissions before delivery, behind a hard tenant equality guard. For patient data that is the right shape — but it is an authorization round trip on the hot path, and at clinical volumes it needs caching we have not yet measured.

OrderingMonotonic per channel; no cross-channel guarantee
TransportsWebSocket and gRPC — no server-sent events, no MQTT
State syncCRDT operations with a logical clock, engine-agnostic on the wire
Change dataLogical replication carries the previous row — a server-side diff channel

07 · Scheduled and durable agent work
librefang / bossfangRust · 31 crates · MIT

An agent operating system: agents that run on a schedule, unprompted. This is where the background work of prior authorization lives — checking whether a payer quietly revised a policy, chasing a disputed attachment, waking a case when an answer finally arrives.

Its durable workflow engine is the best fit in the whole stack for this domain. Prior authorization is a long-running process punctuated by waits on other people. A workflow can pause with a hashed resume token — the plaintext returned once and never stored — and resume weeks later when the payer responds. That is the shape of the actual problem.

SchedulingCron, interval, and one-shot, on a bounded-concurrency tick loop
Run recordDurable, with full per-step history, pause reason, and resume state
RetryPer-step exponential backoff with jitter; fail, skip, or retry per step
IdempotencyKeyed replay of a cached response — but currently on two endpoints only
Dead letterNo dedicated queue; a failed run persists with its error and stops
ChannelsNow out-of-process sidecars — email and webhooks exist; fax, SMS, and payer portals do not

Policy change detection is a pattern here, not a feature. Nothing in the component watches a URL for changes. But the pieces are deliberate: a scheduled job can run a hardened script before the agent wakes, and if that script reports no change the agent turn is skipped entirely — no model spend at all. Poll, hash, compare, and wake only on a real difference. We write the comparison; the runtime provides the discipline around it.

08 · Skills

A skill is a directory containing a Markdown document with structured frontmatter. The runtime discovers them, matches them by trigger, and injects the body into the model's context when one activates.

The dominant execution model is not execution. Of roughly three hundred skills, the large majority are manifest-only — instructions a model reads, with nothing to run. That is why the same skill set works unchanged on a phone: there is no binary to port.

The control that matters here: a model cannot activate a skill by itself. It may request activation through a specific tool that delegates the decision to the trusted host, which checks the request against the run's policy before admitting it.

09 · Decentralized identity Where the roadmap and the code differ.

The intent is that provider organizations exchange authorization evidence directly, each node holding a cryptographic identity and presenting verifiable credentials that prove it may act — rather than routing every exchange through a clearinghouse.

That is a direction, not a shipped capability, and the distinction is worth being exact about. Here is what we found in the code.

BuiltAgent-to-agent invocation with a federated registry and standards-based token authshipped
BuiltPeer-to-peer transport crate with a key-derived node identifiershipped
BuiltFederation bridges to open social protocolsshipped
RoadmapW3C verifiable credentials for owner-to-node delegationplanned
RoadmapPeer discovery, peer transport selection, and routing that can choose a peerplanned
AbsentCross-organization trust registry or partner-to-partner policy delegationunbuilt

One clarification that prevents a common misreading. There is a decentralized identifier scheme in this stack, and it signs WebAssembly build artifacts — it is code signing, not identity credentials. Presenting it as verifiable-credential support would be wrong.

The authorization model also has no organization concept today: four entity types, none of them an organization. Provider-to-provider trust for authorization exchange is entirely unbuilt, and designing it is our work.

10 · What we must build

The runtime stack is general-purpose. Every healthcare-specific integration is ours to write, and none of it exists in any component above.

Absent EDI transactions The standard authorization request, response, and eligibility formats. Zero references anywhere in the stack.
Absent FHIR No clinical interoperability layer. Our EMR connections are a first-party build.
Absent Fax and payer portals Still the dominant submission channels in this domain, and both are greenfield.
Absent Policy change detection A pattern to compose, not a component to configure.

Three risks we would rather name than discover later:

Risk 01 Mobile realtime is the weak leg The entity layer's Flutter package is solid and published. The realtime component's Dart bindings are a different story — the synchronous data surface works, and the asynchronous transport is documented as not functional, pending an upstream fix. Mobile live updates need a different path, and we would rather choose it than assume it.
Risk 02 Two retrieval designs, not one The client architecture fixes on-device embeddings at one dimension so vectors survive syncing between a surgeon's devices. Our server corpus uses larger models for published policy. These are two designs with two privacy reviews, and the guidance is explicit that blurring them into one interface is the mistake.
Risk 03 Version and transport assumptions worth checking early The change-data-capture component targets PostgreSQL 17 while our schema targets 18, so replication compatibility needs verifying rather than assuming. Separately, the peer-to-peer wire protocol is unencrypted by design — authenticated against tampering, but not confidential — so it must never carry patient data without a tunnel beneath it. Neither is a blocker. Both are the kind of detail that becomes one if nobody writes it down.

Every claim on this page was read from source. Where a capability is marked planned or unbuilt, that reflects the code as inspected — not a judgement about the roadmap.
