Reference · Data model

Sixty tables.
Provenance the database refuses to launder.

PostgreSQL 18 with pgvector 0.8.6 and Ory Kratos as the identity provider. Kratos owns credentials and sessions; this schema owns authority — who may affirm a medical decision, where every sentence of a letter came from, and which of two very different kinds of payer criteria a claim is allowed to rest on.

01 · Governance classes

Not every table carries the same obligation. Four classes run through the schema, and the colour in every diagram below refers to them. A table's class is the fastest answer to "what happens if this row is wrong."

Typed Metadata-driven A *_types parent holds a JSON Schema; the child's data column is validated against it on write. Nine pairs.
Gated Capability-enforced A trigger refuses the write unless the actor holds the clinical capability. An administrator is refused here however much system access they hold.
Append-only Immutable record UPDATE and DELETE raise. What was recorded stays recorded, including the denials.
Relational Ordinary columns One fixed shape, so constraints live in the column definitions where the database can enforce them rather than inside a JSON blob.

03 · Kratos and identity

Kratos owns authentication; this database owns authorization. The join is a single column — users.kratos_identity_id, unique and immutable. One Kratos identity is exactly one application user, forever. Everything Kratos has no opinion on lives here: which practice the person belongs to, what they may do, and whether they hold the credentials to affirm a medical decision.

Email is mirrored onto users for display, search and letterhead. Kratos remains the authority on the verified address, so a mirrored copy that drifts is a display bug — never an authentication one.

-- The join to Ory. UNIQUE and never reassigned. CREATE TABLE users ( id uuid PRIMARY KEY DEFAULT gen_random_uuid(), kratos_identity_id uuid NOT NULL UNIQUE, practice_id uuid NOT NULL REFERENCES practices(id), email citext NOT NULL, -- mirrored for display only full_name text NOT NULL, npi text, -- clinicians only status text NOT NULL DEFAULT 'active' );

Authority resolves through capabilities, not role names. Application code asks user_capabilities whether the actor holds affirm_gate; it never asks whether they are "a surgeon". Adding a fourth role therefore requires no call-site change.

The administrator row is the point. Dana Whitfield can add an EMR connection, invite a surgeon and read the audit log, and cannot affirm a gate or sign a letter. That is not an org-chart convenience; it is the safety boundary the whole role model exists to draw.

04 · The typed pattern

Nine *_types / things pairs. The pattern is applied where instances genuinely differ in shape and withheld where they do not — an MRI report, an HbA1c result and a supervised-therapy note share a lifecycle and share almost no fields, which is exactly the case the pattern exists for.

Parent · type registry document_types Configuration data. New document types are added by an administrator without a migration; the JSON Schema they supply becomes the write-time contract.
iduuid, primary key
name *text, unique
descriptiontext, optional
key *text, unique · kebab-cased from name
schemajsonb · JSON Schema for the child payload
created_at *timestamptz, default now()
updated_attimestamptz · set by trigger
Child · instances documents The shared columns are the ones every document type has regardless of payload: a clinical date, an author, a source system and a content hash.
iduuid, primary key
document_type_id *uuid → document_types.id
name *text
datajsonb · conforms to the type's schema
effective_date *date · the clinical date, not retrieval
content_sha256bytea · basis of custody proof
created_at *timestamptz, default now()
updated_attimestamptz · set by trigger

The key is derived, not typed by hand. A trigger kebab-cases name when key is not supplied, so CT Myelogram Report becomes ct-myelogram-report. Application code switches on the key and never on the display name, so renaming a type for the interface cannot break the code that depends on it.

Validation is a trigger, not a CHECK constraint. This is forced by Postgres: a CHECK must be immutable and row-local, and resolving the type's schema means reading another table. Attempting it fails with cannot use subquery in check constraint. A BEFORE INSERT OR UPDATE trigger is the sanctioned mechanism, and it can name the offending type in the error, which a constraint violation cannot.

-- One generic function serves every typed table. CREATE TRIGGER documents_validate_data BEFORE INSERT OR UPDATE ON documents FOR EACH ROW EXECUTE FUNCTION validate_typed_payload('document_types', 'document_type_id'); -- Writing a lab result without its required fields: ERROR: data does not conform to the JSON Schema for document_types type "Laboratory Result"

Where the pattern is deliberately not used: cases, letters, receipts and users have one fixed shape each. Burying a NOT NULL business rule inside JSONB would trade a constraint the database enforces for one nobody does.

05 · The surgeon gate

The product's central claim is that the gate is a hard gate enforced in code, not advice. The schema honours that literally: the rule lives in the database, so a future API route, a batch job, or somebody at a psql prompt cannot route around it.

Four affirmations, each recorded individually with who and when. cases.gate_affirmed_at is derived by trigger from those four rows — it is never written directly, so the denormalized flag cannot disagree with the affirmations behind it. Withdraw one affirmation and the gate clears on the same statement.

-- Only a holder of the clinical affirm_gate capability may affirm. CREATE TRIGGER gate_affirmations_authority BEFORE INSERT OR UPDATE ON gate_affirmations FOR EACH ROW EXECUTE FUNCTION enforce_gate_authority(); -- The administrator, attempting it: ERROR: user a0000000-…-0002 may not affirm the surgeon gate; affirm_gate is a clinical capability -- And downstream, a letter signed before the gate: ERROR: case d0000000-…-0002 has not been affirmed at the surgeon gate; a letter may not be signed

affirmed_by is NOT NULL and ON DELETE RESTRICT rather than SET NULL. Deleting a user must not be able to quietly turn an affirmation into an anonymous one: an affirmation without an affirmer is not a weaker record, it is a false one.

06 · Claim provenance

A surgeon annotation is the one mechanism by which a claim enters a letter without a chart document behind it. That makes provenance load-bearing rather than cosmetic, and it is why annotations is a separate table from case_evidence instead of a flag on it.

-- Every claim traces to exactly one source. The XOR is what stops -- surgeon opinion from being rendered as though a chart said it. CREATE TABLE letter_claims ( claim_text text NOT NULL, document_id uuid REFERENCES documents(id) ON DELETE RESTRICT, annotation_id uuid REFERENCES annotations(id) ON DELETE RESTRICT, CONSTRAINT letter_claims_one_source CHECK ( num_nonnulls(document_id, annotation_id) = 1) );

is_included is separate from existence. A surgeon may record a point for the record, for a peer-to-peer, or for a future appeal without arguing it in this letter. Recording a thought and arguing it are different acts, and the schema does not conflate them.

Evidence carries three states, never two. met, gap and void are a lookup table rather than a boolean because "not documented" is not a weak "not met" — one is a chart that says no, the other is a chart that is silent, and they call for opposite actions: argue, or go obtain.

met Met A dated source document satisfies the criterion.
gap Not met A document exists and it contradicts or falls short. Argue it.
void Not documented Nothing addresses it at all. Nothing has been disproved; obtain it.
07 · Custody and audit

From the submission-and-receipt addendum: the question is not "did we send it" but "can we prove what the payer received". Every attachment carries a page count and a hash taken at the moment of transmission, and receipt_items records acknowledgement per item — so a payer that acknowledges 38 of 42 pages leaves four disputed rows, and those four are the worklist.

custody_events chains each row's hash to the previous one, so a silent edit anywhere breaks verification from that point forward. Both it and audit_events refuse UPDATE and DELETE outright.

The audit log stores actor_label and actor_role as text captured at the time of the act. This is deliberate denormalization: an entry that renders as "Staff did X" because the person was demoted a year later is a false record of what happened.

ERROR: audit_events is append-only; UPDATE is not permitted

Denials are recorded, not only successes. audit_events.outcome carries denied, and a partial index keeps that slice cheap to query — "who tried to sign something they could not" is a question the practice should be able to answer.

08 · Tenancy, multi-EMR and RLS

A surgeon operates at more than one site, so one human patient legitimately exists in several EMRs under different MRNs. patient_identities models that duplication explicitly with a match_status the product surfaces, rather than silently merging records — a wrong automatic merge is a patient-safety event, not a data-quality nuisance.

EMR connection parameters are typed for the same reason documents are. A FHIR backend-services connection needs an issuer, a JWKS URL and a scope list; an HL7 v2 MLLP link needs a host, a port and a client certificate. Forcing both into one column set produces a table where two-thirds of the columns are NULL on every row and no NOT NULL means anything.

Secrets never enter this database. emr_connection_secrets holds a reference such as vault://… plus an expiry, which is what the interface needs to warn before a token lapses.

Tenancy is enforced by Postgres, not only by the application. The API sets the caller's Kratos identity as a session variable on connection checkout, and row-level security policies read it.

-- Set by the API on checkout, per request. SET LOCAL aso.kratos_identity_id = '…'; CREATE POLICY cases_tenant ON cases USING (practice_id IN (SELECT current_app_practice_ids()));
09 · Criteria provenance

Payer criteria arrive two ways, and they are not the same kind of thing. Some are published — a policy document with a number, a version and a URL, hash-verified against what was retrieved. Others are derived: a surgeon watches forty authorisations and works out what actually gets approved, which the payer has never written down anywhere.

The AMA puts the problem plainly — prior authorisation is "a guessing game. We don't actually know what piece of information the health insurer is looking for." Derived criteria are how a practice stops guessing, and sharing them between surgeons is the most valuable thing this product can do. It is also the most dangerous, which is why the schema treats provenance as load-bearing rather than descriptive.

The original schema could not record a derived criterion at all. policy_criteria hung off a policies row that required a policy number, a version and a source URL. A derived rule has none of those, so recording one meant inventing a fake policy — laundering a surgeon's observation into something indistinguishable from published payer language. That is the same failure the annotation table exists to prevent, reappearing one table over.

The evidence ladder, with what each grade must carry and how it may be used
Grade Must carry Citable as policy Half-life
publishedpolicy_id + section + hash yes—
obtained_by_requestdocument_id + received_at yes—
payer_verbalrecorded_by + recorded_at + call reference no365d
derived_observedpractice_id + observation counts no180d
peer_sharedsource practice + the grade it had at home no180d

Every one of those requirements is a CHECK, not a convention. A payer_verbal criterion with no named recorder and no call reference is rumour, and rumour must not outrank an observation backed by data — so the database refuses to store it.

-- A derived rule is never document-backed. If it were, it would be published. -- This single constraint closes the laundering path. CONSTRAINT criteria_derived_has_no_policy CHECK ( evidence_grade NOT IN ('derived_observed','peer_shared') OR (policy_id IS NULL AND document_id IS NULL)) -- Travelling between practices never upgrades a rumour into a fact. CONSTRAINT criteria_peer_no_promotion CHECK ( origin_grade IS NULL OR evidence_grade = 'peer_shared')

Derived knowledge decays, so the schema makes it decay. A peer-reviewed study documents physicians gaming prior-auth protocols until payers notice and rescind them — meaning a rule observed two years ago may be actively wrong today. Retrieval rank blends similarity with grade and an exponential recency decay: a fresh derived criterion scores 0.64, the same criterion unconfirmed for two years scores 0.0385, and current published policy scores 1.0. It cannot quietly outrank the written rule.

PostgreSQL 18's WITHOUT OVERLAPS exclusion constraint also fixes a latent bug: nothing previously stopped two versions of one rule being in force on the same date, which made "what governed on the date of service" ambiguous.

Sharing is aggregate-only, and the antitrust block is structural. DOJ/FTC health care policy statements treat competitors sharing clinical information about the "mode, quality, or efficiency of treatment" as low risk, and sharing fee or reimbursement information as high risk. So the shared table has no money column, no fee column, no allowed-amount column — and an event trigger refuses any future ALTER TABLE that adds one. A price cannot be shared because there is nowhere to put it.

It also carries no case foreign key, no MRN, no date finer than a quarter and no procedure code finer than a family, with a minimum cell size of ten observations from at least two independent practices. Counts are recomputed from observations rather than typed in, one case counts once, and a Wilson lower bound is stored beside the raw numbers so n=3 never presents the way n=300 does.

10 · Retrieval and embeddings

Seven corpora, each answering a question somebody actually asks mid-case: what the payer requires, what actually gets approved, where in three hundred chart pages the evidence for criterion 3.2 sits, how this surgeon argued the point last time, what wording was approved before, why this payer denies, and which society guideline supports the appeal.

Several embedding models must coexist, so the model partitions the search space. A vector column's dimension is fixed at CREATE TABLE and cannot be altered in place, and cosine distance between vectors from two different models is a number with no meaning. Storage is split by dimension class because pgvector indexes vector only to 2000 dimensions and halfvec to 4000 — text-embedding-3-large is 3072 and cannot live in an indexed vector column at all. One shared column would either cap the product at 1536 dimensions forever or silently lose the index, which still returns correct answers and so is not noticed until production is slow.

An embedding of clinical text is PHI. Text can be reconstructed from an embedding by inversion attack, so embeddings fail both Safe Harbor and Expert Determination — they are not de-identified by virtue of being numbers. Each model therefore records whether it is cleared for PHI, a model may only be cleared if it is local or covered by a BAA, and a trigger refuses to store a vector of patient text against an uncleared model. A chunk in a PHI corpus must name its practice, or row-level security would have nothing to filter on.

ERROR: model "OpenAI text-embedding-3-small" is not cleared for PHI; an embedding of clinical text is PHI and is recoverable by inversion ERROR: corpus document contains PHI; a chunk without a practice_id would be visible to every tenant

Retrieval is hybrid. Dense vectors miss exact tokens that decide cases — L4-L5, a CPT code, HbA1c are either present or not, and cosine similarity is indifferent to that — so keyword search runs beside the vectors and the two rankings fuse by reciprocal rank.

The letter boundary is enforced, not hoped for. A rule about what a model should write is not a rule. Every retrieval into a generation context is logged; letter_claims gained a criterion source, so a criterion-backed claim finally has a legal slot instead of having to masquerade as a document; and a letter cannot be signed while a non-citable criterion sits unresolved in its retrieval log. Attributing a derived criterion as published policy raises.

ERROR: criterion f0000000-… is graded "derived_observed" and may not be presented to a payer as published policy ERROR: 1 unattributed non-policy criteria were retrieved into this letter; attribute or exclude each before signing
11 · Adversarial review Judged by a different model than the one that wrote the schema.

This design was reviewed before it was written, by k3 — a different model from the one that produced it, given only the design and no conversation history. It returned BLOCK at confidence 82, with four critical findings. Every one was a real hole, and each is now closed by a constraint rather than by a paragraph.

K3-1"The antitrust block is not structural — a regex over free text is trivially evaded"closed
K3-2"Cross-tenant observation linkage leaks PHI and defeats the existing RLS"closed
K3-3"Nothing binds generated letter text to the criteria that informed it"closed
K3-4"Decoupling from policies strips effective dating; a stale rule ranks equal to current policy"closed
K3-5"Observation counts are gameable and unverifiable"closed
K3-6"Criterion text stays mutable, so observations silently endorse edited text"closed
K3-7"The ladder conflates provenance with reliability; payer_verbal is unverifiable hearsay"closed

The review's eighth item claimed the existing signing triggers would break when policy_id became nullable. That part was wrong — no trigger validated criteria against policies. But checking it surfaced something worse: letter_claims_one_source was a strict two-way choice between a document and an annotation, so a criterion-sourced claim had no legal slot at all and could only enter a letter disguised as one of the other two. The laundering path was already in the code.

13 · Known limits

Three things a reviewer should know before this goes near production data.

Limit 01 Free-text fee screening is a tripwire, not a barrier The structural antitrust block is real — the shared corpus has no column for a price. But a dollar figure typed into a criterion's free text is a different problem. A trigger flags obvious currency patterns and blocks a flagged criterion from ever reaching the shared corpus, and it is honest about what it misses: 1.8x Medicare, six thousand and RVU-weighted all pass. Treating that screen as a guarantee would be worse than not having it. Human review before sharing remains required.

Separately, JSON Schema validation stays partial — jsonschema_basic_check enforces type and required properties, not the full specification. Production should install pg_jsonschema; the trigger wiring does not change.
Limit 02 No PHI encryption at rest This schema assumes volume or tablespace encryption beneath it. Column-level encryption for identifiers, and the key-management decision behind it, is a separate piece of work that should not be inferred from this file.
Limit 03 Seed data is structural, not clinical The document types, pathway types, QA checks and roles seeded in schema.sql encode the workflow the prototype demonstrates. The JSON Schemas attached to them are plausible and internally consistent, but they have not been reviewed against a specific payer's published medical policy. Treat them as the shape of the answer, not the answer.
