This product ships as web, desktop, and mobile. Not three products — one architecture with three implementations, built under a set of enforcement contracts that decide the order of work and what "finished" is allowed to mean.

01 · The control loop

The method is not "plan, then build." It is a loop with a named producer, an independent critic, and a verification gate that a producer is not permitted to pass on its own work.

learn → assess → research → decision-complete plan → bounded implementation → public-boundary verification → adversarial critic → retention → next

Four rules govern it, and they are stated as prohibitions because that is how they get broken:

01 Do not implement first When requirements, domain knowledge, or architecture boundaries are incomplete, the loop starts with learning and assessment. In this domain that is not ceremony — the difference between a gap and a void is a domain fact that changes the schema.
02 A producer cannot certify its own work The critic is a different reviewer with fresh context. This page's own database design was reviewed that way, and the review returned four critical findings that changed the schema.
03 Authority is declared before implementation What may be read, written locally, written externally, destroyed, published — stated up front. Work stops at the boundary rather than expanding through it.
04 Requirements are never rewritten to fit a failing output If the result does not meet the requirement, the result is wrong. This is the rule that keeps a demo from quietly becoming the specification.
02 · What kind of build this is

The playbook classifies a product before planning it, because the classification determines which contracts apply. This one is a composite of three.

Scenario 01 Full hybrid Web, desktop, and mobile from one architecture, with a shared core.
Scenario 02 Multi-tenant Practices are tenants. Every data scope carries a tenant predicate bound to the verified session.
Scenario 03 Local inference Because patient text should be able to stay on the device — which makes engine choice a privacy decision.
03 · Order of work Two of these phases are irreversible.

The ordering is not a preference. Phases one and two are load-bearing for everything downstream — retrofitting a privacy class or a session boundary means rewriting the schema and the gateway. Everything from phase five onward is comparatively cheap to redo.

Phase 0Control and process

Classify the product, emit the reference manifest, declare authority, and name the producer and the independent critic. Pin every dependency version in one file before the first manifest is written — doing it later is a migration; doing it now is free.

Phase 1 · irreversibleData and privacy contracts

Before the first table exists. Every datum gets a lane — server authoritative, collaborative, or append-only history — and a privacy class. An unknown class defaults to local, and local data is structurally refused at the sync boundary rather than filtered out. In this product that decision governs every chart document and every embedding derived from one.

De-identified development data is stood up here too, before anyone touches real records — and on the principle that a replica is not anonymous merely because names and email addresses were removed.

Phase 2 · irreversibleSecurity and identity

Before any agent or endpoint. The verified session, the governed tool sequence, and the personas. Every tool call an assistant makes passes eight ordered steps — resolve identity, validate against schema, classify effects independently of what the tool claims about itself, evaluate policy, confirm when required, execute with idempotency and cancellation, redact, and append an immutable audit record.

The rule that matters most here: tool names and descriptions are untrusted data. A tool that describes itself as safe is making a claim, not a guarantee.

One token file generates both the web theme and the mobile theme. This is generated rather than kept in sync for a documented reason: when the two were hand-mirrored they had already drifted — two different values for the same background role, with nothing in the build to notice. 04 · Three surfaces, one architecture

What is shared is the contract, not the code. Each surface owns its own presentation idiom; they agree on the entity schema, the design tokens, and the event vocabulary.

Web · React 19 Component → feature hook → entity layer → transport → local store, with PostgreSQL compiled to WebAssembly running in the browser. The layering is lint-enforced, not merely encouraged.
Desktop · Tauri 2 The same React bundle, the same engine natively through typed commands. The window chrome is conditionally rendered — shipping the desktop title bar into a browser is a crash, not a cosmetic slip.
Mobile · Flutter Widget → provider → entity package → bridge → Rust store, over SQLite. A hand-written parallel implementation of the same contract, verified against the same scenarios.
Shared The entity schema and its intermediate representation, the design tokens, the block contract, and the event envelope. Every generator consumes the same representation so the targets cannot diverge.

Navigation is decided by window width, not by operating system. Top-level destinations go in a bottom bar on every platform; a rail appears when the window is wide enough to justify one. A platform check in navigation code is the bug the rule exists to prevent.

05 · Where a turn runs

The engine is a per-device choice. The lane is a per-turn choice. They are different decisions, and neither is "mobile versus desktop." Every engine sits behind one interface, so no surface code branches on which one is present.

Inference engine per device, and why each was chosen
SurfaceEngineWhy this one
Desktopllama-cppPinned, checksummed weights. Zero-configuration default.
AndroidLiteRT-LMRuns everywhere on CPU — the correctness baseline.
iOSMLX-SwiftReaches the GPU without the alternative's build surface.
macOSMLX-CIn-process, no separate language runtime.
WebWebLLMBrowser GPU lane, no key required.

Android is deliberately not the same engine as desktop, and the reason is instructive. The desktop engine builds for Android, so it looks like the obvious single mobile choice — but its GPU path proved device-specific: it works on the phone you tested and fails on the next one. That is the worst possible failure shape for a correctness baseline, so the universal CPU engine is the Android default.

Three lanes, and an unknown lane is rejected loudly rather than defaulted — because on the cloud lane, defaulting means patient data leaving the device.

Lanecloud A remote provider under the practice's own key. Never the zero-configuration default.
Lanelocal On-device. The lane for anything touching patient text.
Laneruntime The governed agent runtime. On mobile it is embedded as a library, never a background service.

Model files are revision-pinned and hash-verified before first load, small files fetched first so a bad revision fails in seconds rather than after gigabytes, and memory is checked before a load rather than around it — because on iOS an over-budget model load does not raise an error. The operating system kills the process.

06 · What syncs, and what never does

The device never mirrors the server database. Every record belongs to exactly one lane and one privacy class, and getting the lane wrong is the root cause of most synchronization defects.

For this product the consequential rule is a single sentence: an embedding of local data is itself local. We reached the same conclusion independently from published research on reconstructing text from embedding vectors — which is a good sign that the rule is right, and the reason the database refuses to store a vector of patient text against a model that is not cleared for it.

Offline writes go through one durable queue with explicit states, and an action that exhausts its retries becomes visible to the user rather than disappearing. A failure that no one sees is worse than one that fails loudly.

07 · What "done" is allowed to mean

"Working" is a runtime claim, not a synonym for type-checking or passing unit tests. Nothing is called working, complete, ready, or shipped until every gate below passes on every surface being claimed.

01Reproducible from a fresh clone — no leftover build output, downloaded model, or tool cacherequired
02Frozen dependency install and code generation both succeedrequired
03Formatter, type checker, architecture audit, and compiler all passrequired
04A production build succeeds from tracked sourcesrequired
05The built artifact actually starts and reaches its documented ready staterequired
06Expected data directories exist and are readable after launchrequired
07One real user-visible workflow crosses the public boundary and returns a valid resultrequired
08A physical device run, whenever a platform baseline or inference lane changedrequired

A simulator is not a device for this purpose. The reason is specific: the failures that matter here are invisible to a host check. An over-budget model load on iOS produces no exception and no log — the process is simply killed. A mismatched native library on Android surfaces only when the bridge is first touched. Native bridges bind by symbol name, so a renamed class path compiles clean on both sides and fails to resolve at runtime.

Results are recorded in four words, and only one of them means finished:

ResultPassed The production artifact launched and the workflow completed.
ResultBuild-only It compiled but was never launched. Never call this working.
ResultBlocked An unavailable dependency or target prevented proof.
ResultFailed It ran and produced incorrect behaviour.

A device record names the device, the operating system version, and what was actually observed. "Tested on Android" is not a record — it cannot be reproduced and it cannot be falsified. And a newly generated project starts unverified on purpose: that is not a gap to paper over, it is an accurate statement until someone runs it on hardware.

08 · What adopting this commits us to

These contracts assume a specific project scaffold — a version manifest, an audit script, a token generator, a platform-support record, and a particular core library layout. They are enforcement contracts for an existing architecture, not a greenfield generator.

Adopting them means adopting that scaffold, or reimplementing its file layout deliberately. We would rather state that plainly than let a reader infer that the gates come free.

Tension 01 A vault that is gone by design The collaborative-document lane is explicit that if a user loses every paired device, their vault is gone — no automatic cloud backup, by design. That is excellent privacy engineering and it conflicts directly with medical-record retention obligations. The resolution is that clinical records are not vault data; only genuinely personal preferences are. Worth deciding once, in writing, rather than per feature.
Tension 02 On-device retrieval versus a server corpus The client contract fixes one embedding dimension so vectors survive syncing between a surgeon's own devices. Our server-side corpus for published policy uses larger models. The guidance is explicit that these are two designs with two privacy reviews — so we treat them as two, rather than pretending one interface covers both.

One last rule, and it is the reason this page exists at all: it is a blocking failure to implement only the easiest routes while presenting the shell as the finished application. Navigation items may not lead to placeholders. Every screen in the prototype you are reading is reachable, and every one of them renders real content.
