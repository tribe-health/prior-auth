What ARCH-001 omitted

The shell design has no presentation plane. Every plugin in its inventory provides data or capability; none provides UI. The criteria matrix and the affirmation gate — the two things a physician actually touches — were specified as functionality with no account of how they render.

That omission is not neutral. The safety argument in ARCH-001 says the renderer cannot activate unless the gate provides aso.affirmation. But what the gate provides is a signed attestation, and what makes that attestation meaningful is that a surgeon read a criteria matrix with source citations attached and affirmed it. If the surface that displays the matrix is a hand-built view sitting outside the runtime, then the runtime guarantees the attestation exists while guaranteeing nothing about what produced it.

The restatement

The safety property is not "no letter without an affirmation record." It is "no letter without a physician having seen the criteria matrix, with citations, and affirmed it." Closing the distance between those two sentences is what the UI plane is for.

UI is a coeffect, not a layer

A plugin does not ship widgets and does not import a UI framework. It provides an A2UI surface descriptor — a declarative artifact reference plus props — through an ordinary revertible effect, and the shell materialises it natively.

// A plugin contributes a surface the same way it contributes anything else
fn apply(ctx: &Ctx, cfg: Config) -> Result<()> {
    ctx.surface(Surface {
        id:      "aso.criteria.matrix",
        schema:  "a2ui.panel@1",
        slot:    Slot::Primary,
        title:   "Criteria Matrix",
        blocks:  BlockSource::Stream(matrix_stream),
        actions: vec!["criteria.recheck", "criteria.open_source"],
    })?;   // inverse: unregister the surface
    Ok(())
}

ctx.surface is not a new primitive. It is a thin wrapper over ctx.effect that registers with the surface broker and returns the unregistration as its inverse. That means temporal composability applies to the interface for free:

Unload the appeals plugin and the Appeals surface disappears from navigation. No nav-cleanup code, no dangling route, no orphaned menu entry pointing at a component that no longer exists. Navigation registries are a classic leak site precisely because registration and deregistration are written in different places by different people; here they are the same expression.

A2UI describes; AG-UI carries

The two protocols are not alternatives and the division of labour matters for this application specifically.

A2UI
agent → UI · block-centric
The semantic event envelope. 27 event variants mapping one-to-one onto ContentBlock. Describes what a surface is and what it contains. One-directional.
AG-UI
agent ↔ frontend · state-centric
Bidirectional. State sync via JSON Patch, and — the part that matters here — frontend→agent events: interrupts, confirmations, state requests.

The affirmation is an AG-UI client event. Not a Tauri command, not a REST call, not a callback the renderer invents. It travels the same channel as every other frontend→agent event, is routed by the same event router, and is therefore subject to the same policy evaluation and the same receipt.

// The affirmation, as it actually crosses the boundary
{
  "type": "AFFIRM_CRITERIA",
  "case_id": "c-8817",
  "matrix_hash": "sha256:9f2c…",      // what was displayed, not what was computed
  "affirmed_rows": ["pt-12wk", "mri-12mo"],
  "declined_rows": [],
  "principal": "did:aso:p:kjames",
  "attested_at": "2026-08-18T15:04:11Z"
}

matrix_hash is the load-bearing field. It is the hash of the rendered surface, not of the computed matrix. If the two diverge — because a plugin mutated the matrix between render and affirmation — the gate rejects the event. The physician affirms what was on the screen.

The surface broker

Multiple plugins contribute surfaces, so the same constraint that forced a broker for ingestion applies: a key has one possible provider, and aso.ui.broker owns it. Plugins register with the broker; the broker composes the shell.

KeyProviderPurpose
aso.ui.brokershell (kernel)Surface registry, slot arbitration, navigation model
aso.ui.channelshell (kernel)AG-UI bidirectional stream, scoped per case realm
aso.ui.themeshell (kernel)Brand tokens from ASO-BRAND-001, resolved per platform

Slot arbitration is where the broker earns its place. Two plugins both wanting the primary slot is a configuration conflict, not a runtime race — the broker resolves it deterministically by entry order in aso.workbench.yaml and reports the conflict rather than letting last-write-wins decide what the surgeon sees.

Lifecycle transitions are the UI state machine

This is the correspondence worth building on. Cordis classifies every context change against a component's specification as activating, deactivating, or neutral. AG-UI carries lifecycle events. They are the same events.

Fiber transitionAG-UI emissionWhat the surgeon sees
L-BeginRunStarted · SurfacePendingSurface appears in a loading state
L-IterStateDeltaRows populate as extraction lands
L-FinishSurfaceMountedSurface interactive
L-RaiseRunError · SurfaceFailedSurface shows its own failure, siblings unaffected
L-LeaveSurfaceLeavingSurface disabled but still visible during teardown
L-UnloadSurfaceUnmountedSurface removed from navigation

The consequence is that there is no separate UI state store deciding what is visible. Visibility is a projection of the fiber registry. Zustand on desktop and Riverpod on mobile hold render state — scroll position, expansion, focus — and nothing about which surfaces exist. A plugin cannot be inactive and visible, or active and missing, because the two facts are the same fact.

L-Leave deserves note. The interval between a fiber ceasing to provide and its inverse running is exactly the interval in which a surface should be visible but non-interactive. That is normally hand-coded disabled-state logic; here it falls out of the withdrawal guard.

Privileged blocks and the impersonation problem

Here is the attack the plane creates and must then close. If any plugin may emit any A2UI block, a plugin can emit something that looks like the affirmation dialog, collect a signature-equivalent gesture, and satisfy the renderer with an attestation the surgeon never knowingly gave. Declarative UI generalises the trust surface, and generalising a trust surface around a legal attestation is the sort of thing that has to be closed by construction rather than by review.

Three mechanisms, layered:

  1. Component allowlist. The renderer accepts only registered A2UI schemas. An unknown schema is dropped, not rendered as a fallback. This already exists in the KnowMe agent runtime standard and carries over unchanged.
  2. Privileged block class. AffirmationBlock may be emitted only by a principal Cedar authorises, which is gate.affirmation and nothing else. Emission from any other fiber is a policy denial recorded in the ledger, not a silent drop.
  3. Kernel-owned chrome. The shell renders the affirmation surface with a frame the emitting plugin cannot style, position, or overlay — the same reasoning that puts OS credential prompts outside application control. The plugin supplies the matrix contents; the shell supplies everything that makes it recognisable as the gate.
Follows for Tier 2

A sandboxed WASM component plugin can emit only from the unprivileged block set. It can contribute a criteria pack, render a worklist, and stream citations. It can never render the gate, and its WIT world cannot import the privileged schema, so this is a link-time fact rather than a runtime check.

One plugin, two renderers

Because a plugin emits a descriptor rather than a component, the same plugin renders on both surfaces without a second implementation. This is the whole point of routing UI through the protocol rather than through a framework.

TJ-ARCH-MOB-001 makes the platform choice for us rather than leaving it open: healthcare and regulated-industry mobile is Flutter + Rust FFI, mandatory — no WebView fragmentation on a device holding PHI. Desktop with generative artifact rendering is Tauri + React. Both surfaces for one product is the hybrid default. The workbench lands squarely in all three rows.

Layer contract, unchanged

Components talk only to hooks; hooks talk to stores; stores talk to IPC. No invoke() in a component, no direct store import in a component, no fetch outside TanStack Query. The UI plane adds a source of truth above that contract; it does not relax it.

Relationship to gen_ui_core

The workbench does not build a second agent runtime. gen_ui_core already carries the Tokio runtime, the A2UI and AG-UI adapters, embedded SurrealDB, the MCP registry, local candle inference, and the UAR in embedded mode. Several ARCH-001 plugins are thin wrappers over facilities that already exist there.

What the workbench adds that gen_ui_core does not yet have is aso-runtime: the fiber machinery, the accumulator, the withdrawal guard, the reactive resolution. That is the honest framing of this project's platform value — the workbench is the prototype of a plugin plane that gen_ui_core needs and KnowMe needs, built first against a bounded single-tenant application where the blast radius of getting it wrong is one surgeon's letter queue rather than a marketplace.

If it survives that, it graduates into gen_ui_core and every downstream consumer inherits it. If it does not, the cost was contained.

Costs and limits

Descriptors add an indirection

Debugging a layout means reading a descriptor and a renderer instead of one component. On a small team this is a real drag on iteration speed, and it is the standard tax on any declarative UI protocol. The mitigation is a descriptor inspector in the dev build, not optimism.

Not everything is expressible declaratively

The source-document viewer with page-level highlighting, and the PDF preview, will not reduce to a block schema without contorting it. Those get a native escape hatch — the registered render slot, where the agent controls when and with what props a hand-written widget renders. That mechanism exists for exactly this and should be used sparingly and named explicitly in the surface descriptor so an escape hatch is never mistaken for a schema.

Mobile affirmation is a compliance question, not a technical one

The plane makes it technically possible for Kevin to affirm a criteria matrix from an iPad between cases. Whether he should is a separate matter involving device management, screen-lock policy, and a defensible position on attesting that the person holding the device is the credentialed surgeon. Do not ship mobile affirmation in v1. Ship mobile review — the matrix, the gaps, the case list — and keep the gate on the desktop where the signing key and the physical context are.

Building the plane as A2UI now costs almost nothing extra and preserves the option for when that question has an answer.

The privileged-block mechanism is only as good as the chrome

Kernel-owned chrome stops a plugin from drawing a convincing fake gate inside the app. It does not stop one from drawing a persuasive prompt elsewhere in the interface that leads the surgeon to affirm without reading. That is a design-review obligation on every surface, not something the runtime can enforce, and it should be stated in the review checklist rather than assumed away.

Build order deltas

ARCH-001's sequence stands. Four insertions, placed so the gate's surface exists before anything can compose a letter.

The test that replaces ARCH-001's stage 6 test

The original test was: remove the gate from configuration, assert the renderer never reaches Active. That still holds and is still necessary. It is no longer sufficient.

The test that matters now is: a plugin other than gate.affirmation emits an AffirmationBlock, and the renderer never receives it, the surgeon never sees it, and the attempt appears in the ledger. If that passes, the safety property covers the pixels and not merely the record.
